# MCP Gateway 产品需求规格：用户场景

> 本文是产品需求入口。新任务应先阅读本文了解用户可见范围，再阅读 [顶层架构、概念设计与交付方案](mcp-gateway-top-level-architecture.md)。

## 1. 文档目的

本文以产品需求规格的方式，从用户和调用方视角梳理工作区产品的目标、角色、用户场景、用户可见流程、结果和验收标准。最终对外提供统一 HTML 控制台和 MCP 服务接入；二者共享同一套工作区能力。底层远程仓库统一使用 Git，但 Git、Repo、SSH 实现和 k3s 资源不属于用户界面概念。

## 2. 目标与非目标

### 2.1 目标

- 工作区的源码范围由系统内部配置维护，用户不需要在代码仓库中维护项目配置文件。
- MCP Gateway 作为系统启动项运行，提供持续可用的本地 MCP 服务，而不是按请求临时启动的脚本。
- 交付、安装、升级和运维的核心对象是 Gateway 服务本身及其用户级配置。
- 对用户提供统一 HTML 工作区控制台，以及供 codexcli/自动化接入的 MCP 服务配置。
- MCP 服务同时提供代码分析、知识检索、工作区服务和维护能力，而不是只提供代码分析工具。
- 远程仓库统一通过 Git 管理，支持 Codeup SSH 和 GitHub SSH；用户只需准备并配置本地 SSH key。
- 底层 MCP 后端、镜像、Job 模板、资源限制、超时、并发和安全策略集中在用户级 Gateway 配置中。
- 对 codexcli 暴露稳定、数量受控的高层工具契约：
  - `code_architecture_analysis`
  - `code_symbol_query`
  - `code_refactor`
  - `knowledge_search`（代码、项目文档和本地知识库的统一检索）
- 底层 CodeGraph、Serena、RAG 和 k3s 调度细节对项目开发者透明。
- 同一 Gateway 配置可以被多个项目复用，并允许用户在本地对单个项目做非仓库级覆盖。
- 对长时间运行、资源泄漏、并发写入和路径越界提供明确的保护。

### 2.2 非目标

- 不允许项目配置选择后端或修改全局能力策略。
- 不将用户级镜像、k3s 模板、RBAC 和运维参数提交到业务仓库。
- 不要求 codexcli 直接理解 CodeGraph、Serena、RAG 或 Kubernetes API。
- 不要求用户直接操作 Git 命令、Repo 路径、分支、commit、PVC、Pod 或 Job。
- 不在用户界面中暴露 SSH 私钥；私钥不能写入项目仓库或持久化工作区。
- 不在本阶段规定文档索引的具体存储引擎、embedding 模型或分块算法。
- 不在本阶段规定具体后端实现、embedding 模型或源码分析算法。

## 3. 用户角色

| 角色 | 关注点 | 主要操作 |
| --- | --- | --- |
| 项目开发者 | 低配置、可预测的工作区能力 | 使用 HTML 控制台或 MCP 能力 |
| codexcli | 稳定的 MCP 契约 | 通过 MCP 发起服务、维护和代码能力调用 |
| 本地用户 | 服务持续可用 | 安装、启动、停止或查看 Gateway 服务状态 |
| SSH 配置用户 | 远程仓库可访问 | 配置 Codeup 或 GitHub 对应的本地 SSH key |
| Gateway 运维者 | 全局能力、资源和安全 | 管理用户级 config、模板、镜像和策略 |
| 后端维护者 | 单个底层能力的实现 | 发布或替换 CodeGraph、Serena、RAG |
| 集群管理员 | k3s 资源和权限 | 提供 PVC、RBAC、配额和运行环境 |

## 4. 核心用户场景

### 场景一：通过统一 HTML 控制台进入工作区

**用户**：项目开发者
**目标**：通过一个入口查看和操作所有工作区，不接触 Git 或 k3s 实现细节。

**主流程**

1. 用户打开工作区 HTML 控制台。
2. 用户查看工作区列表、当前状态和最近任务。
3. 用户选择一个工作区进入详情页。
4. 用户浏览文件、查看分析结果、检索代码/文档或发起维护操作。
5. 用户查看任务进度、成功结果和需要处理的异常。

**成功结果**

- 用户始终使用“工作区”这一统一概念。
- 页面不要求用户输入本地仓库路径、Pod、PVC、Job 或 Git 命令。
- HTML 控制台与 MCP 服务看到的是同一份工作区状态。

### 场景二：添加远程工作区

**用户**：项目开发者  
**目标**：将一个远程代码项目加入工作区，而不需要了解 Git 实现。

**前置条件**

- Gateway 服务已经随系统启动并处于健康状态。
- 用户已经配置可访问目标远程仓库的 SSH key。

**主流程**

1. 用户在 HTML 控制台选择“添加工作区”。
2. 用户选择远程平台类型，例如 Codeup 或 GitHub。
3. 用户填写远程仓库地址和工作区显示名称；系统使用用户已配置的本地 SSH key。
4. 用户提交添加请求，等待工作区准备完成。
5. 用户进入新工作区查看文件和可用能力。

**成功结果**

- Git clone、远程连通性检查和工作区准备由系统完成。
- 用户不需要输入私钥内容、选择内部密钥文件或执行 Git 命令。
- Codeup SSH 和 GitHub SSH 使用同一套工作区操作体验。

### 场景三：系统启动后使用常驻 Gateway

**用户**：本地用户 / 系统管理员  
**目标**：系统启动后无需手工运行脚本，codexcli 即可连接 Gateway。

**主流程**

1. 用户启动操作系统或 WSL 环境。
2. 用户查看 Gateway 状态，确认服务处于可用状态。
3. 用户打开 HTML 控制台或 codexcli，不再手工运行 Gateway 启动脚本。
4. 用户直接选择工作区并使用代码、知识或维护能力。
5. 用户在需要时查看服务状态、错误信息或重启结果。

**期望行为**

- Gateway 进程异常退出时由系统服务管理机制自动重启。
- 配置错误、k3s 不可用或 PVC 不可用时，服务应报告不可用原因，而不是假装启动成功。
- 服务停止或升级时，不应遗留未受控的 Job、锁或并发计数。
- 日常使用不需要为每次 MCP 调用重新启动 Gateway。

### 场景四：执行架构分析

**用户**：codexcli / 项目开发者  
**目标**：获取项目架构、依赖或模块关系分析。

**主流程**

1. 用户在 HTML 控制台或 codexcli 中选择目标工作区。
2. 用户选择“架构分析”，并指定关注范围或问题，例如模块依赖、入口和分层关系。
3. 用户提交分析请求并查看进度。
4. 用户查看架构图、模块关系或文字分析结果。
5. 用户根据结果继续追问、缩小范围或转到符号查询。

**成功结果**

- 调用方不感知具体镜像、Pod 地址和 Job 名称。
- 后端替换时，高层工具名称和工作区使用方式保持不变。

### 场景五：查询符号或执行重构

**用户**：项目开发者  
**目标**：查找符号定义、引用，或安全地执行 rename 等写操作。

**主流程**

1. 用户在工作区中输入要查找的符号、引用或代码位置。
2. 用户选择“符号查询”，查看定义、引用和相关文件。
3. 如需修改，用户选择“重构”，指定操作类型、目标符号和修改范围。
4. 用户预览待修改文件和变更摘要。
5. 用户确认执行，或取消并返回修改参数。
6. 用户查看执行结果，并检查工作区中的代码变更。

**成功结果**

- 同一仓库不会同时执行互相覆盖的 Serena 写操作。
- 写操作失败时明确返回失败原因，不返回伪成功结果。

### 场景六：检索代码、文档和本地知识

**用户**：项目开发者  
**目标**：通过自然语言检索源码、项目文档和用户配置的本地知识库内容。

**主流程**

1. 用户在 HTML 控制台或 codexcli 中输入自然语言问题。
2. 用户选择检索范围：代码、项目文档、本地知识库，或全部来源。
3. 用户提交查询，并按需要设置结果数量或文件类型过滤条件。
4. 用户查看结果摘要、来源类型、文件/文档位置和相关性。
5. 用户打开命中内容，或继续追问以缩小检索范围。

**成功结果**

- `knowledge_search` 统一检索代码、Markdown/API 文档、设计资料和用户维护的本地知识库。
- 调用方可以区分 `code`、`doc`、`knowledge` 等来源类型，也可以请求跨来源检索。
- 项目不需要启用或配置向量检索。
- RAG 或 embedding 实现可以在用户级配置中演进。

### 场景七：维护工作区

**用户**：项目开发者 / 工作区管理员
**目标**：更新工作区、切换工作版本、同步远程变化或查看工作区状态，但不直接操作 Git。

**主流程**

1. 用户在 HTML 控制台选择目标工作区。
2. 用户选择“检查更新”“同步工作区”“切换版本”或“查看状态”等维护操作。
3. 用户按业务含义选择目标版本或同步方式，不输入 Git 命令。
4. 用户确认操作，查看进度和风险提示。
5. 用户查看工作区状态、变更摘要和代码/知识索引是否可用。

**期望行为**

- 系统在存在未保存变更、冲突或正在执行代码任务时给出明确提示。
- 高风险覆盖、丢弃变更或删除工作区操作必须二次确认。
- 用户看到工作区状态和可执行建议，不看到 Git 命令、仓库路径或内部任务对象。

### 场景八：用户为单个工作区临时切换策略

**用户**：Gateway 运维者或高级开发者  
**目标**：在不修改仓库的情况下验证其他后端。

**主流程**

1. 高级开发者确定需要针对某个工作区临时验证不同能力策略。
2. 高级开发者在 HTML 控制台或本地用户配置中创建该工作区的覆盖项。
3. 高级开发者重新发起同一能力请求进行对比。
4. 高级开发者查看差异并决定保留或删除本地覆盖。

**成功结果**

- 覆盖只影响当前用户和指定项目。
- 覆盖文件不会进入 Git，也不会改变其他项目的默认策略。

### 场景九：任务超时或后端异常

**用户**：所有调用方  
**目标**：在后端不可用、任务卡死或资源不足时快速失败并回收资源。

**期望行为**

- Gateway 为创建 Job、等待后端、读取结果分别设置超时边界。
- 超时后主动删除 Job 或执行等价清理操作。
- 后端连接失败、配置错误、权限错误和结果解析失败需要区分返回。
- 不以空结果、默认成功或部分未标记结果掩盖异常。
- 清理失败需要记录可诊断信息，并保留后续人工处理所需的标识。

### 场景十：服务不可用、工作区配置非法或权限不可用

**用户**：项目开发者 / Gateway  
**目标**：区分常驻服务故障、错误配置和路径穿越，阻止它们影响集群或其他项目。

**期望行为**

- 工作区不存在、配置不完整或工作区状态非法时拒绝调用。
- Gateway 未运行、未健康或无法连接 k3s 时，调用应返回服务不可用状态和诊断信息。
- Codeup/GitHub SSH 凭据不可用时，应提示用户配置或选择对应的本地 SSH key。
- 用户不应通过错误信息看到私钥、远程凭据、仓库内部路径或集群对象名称。
- 错误信息指出修复方向，但不泄露集群凭据或敏感配置。

## 5. 统一用户体验要求

1. **配置最小化**：用户只需配置工作区来源和本地 SSH 访问能力。
2. **服务常驻**：Gateway 随系统启动、可健康检查、可自动重启。
3. **契约稳定**：高层工具参数和结果模型独立于底层后端。
4. **知识统一**：语义检索同时覆盖代码、文档和本地知识库，并明确来源。
5. **默认安全**：资源、权限、超时和并发由 Gateway 统一控制。
6. **结果可诊断**：成功、失败、超时和拒绝均有明确状态。
7. **行为可预期**：相同项目和策略下，调用不会因为后端内部实现细节改变语义。
8. **写操作可控**：所有可能修改源码的能力必须经过仓库级互斥保护。
9. **界面统一**：HTML 控制台和 MCP 服务使用同一套工作区、任务和结果模型。
10. **仓库实现隐藏**：Git 是远程仓库的内部实现，用户只操作工作区和版本等业务概念。

## 6. 验收标准

- 用户可以通过 HTML 控制台添加 Codeup 或 GitHub 远程工作区，并使用已配置的本地 SSH key 完成准备。
- 系统启动后 Gateway 自动运行，健康检查可确认 MCP 端点可用。
- Gateway 服务异常退出后可以按系统服务策略自动恢复。
- 用户可见配置中不存在后端类型、镜像、k3s、Git 命令或向量开关字段。
- `knowledge_search` 至少能返回代码和文档两类来源，并支持按来源过滤或跨来源检索。
- 修改全局后端映射可以替换实现，而无需修改项目文件或 codexcli 调用。
- Job 结束后会按 TTL 自动清理；Gateway 超时会触发主动清理。
- 同一仓库的并发写操作不会同时进入执行阶段。
- 非法路径、非法配置和未知能力会在创建 Job 前被拒绝。
- 后端异常不会被包装成成功响应。
- 用户可以通过 HTML 或 MCP 完成工作区状态查看、更新、同步和版本切换。
- 对用户不可见 Git 命令、远程仓库内部路径、SSH 私钥、PVC、Pod 和 Job 名称。

## 7. k3s 运行环境准入需求

本节只定义 Gateway 正常运行所需的 k3s 环境条件，不描述 Kubernetes 部署方式或具体技术实现。k3s 是系统内部运行环境，不作为用户操作入口。

运行环境必须满足：

1. **集群可用**：提供稳定、可连接的 k3s 运行环境，能够运行 Gateway 所需的工作区和分析任务。
2. **工作区持久化**：提供持久化存储，工作区中的代码、文档和必要索引不会因任务重启而无提示丢失。
3. **工作区隔离**：不同工作区之间相互隔离，一个工作区的任务不能读取或修改其他工作区内容。
4. **远程访问**：运行环境能够访问 Codeup 和 GitHub，并使用用户已配置的 SSH key 完成远程工作区操作。
5. **内部通信**：Gateway 能够访问内部工作区服务和代码能力服务，内部服务不直接暴露给用户或公网。
6. **资源充足**：具备满足并发工作区、代码分析、重构和知识检索任务的 CPU、内存、存储和临时空间。
7. **任务回收**：已完成、失败或取消的任务能够被回收，不长期占用运行环境资源。
8. **安全隔离**：工作区、用户凭据和运行任务受到隔离保护；SSH 私钥不进入代码、工作区或日志。
9. **状态可见**：能够判断集群、存储、远程访问和任务运行是否正常，并向 HTML 控制台和 MCP 返回可理解的状态。
10. **故障可恢复**：k3s、节点、存储或网络短暂异常恢复后，Gateway 能继续提供服务，且不会遗留不可控的工作区任务。

### 7.1 环境准入验收

只有满足以下条件，运行环境才可标记为“已准入”：

1. 可以创建并恢复一个工作区。
2. 可以完成一次代码分析和一次知识检索。
3. 可以使用 Codeup 和 GitHub 的 SSH 配置完成远程工作区操作。
4. 多个工作区可以同时运行且互不影响。
5. 任务完成或失败后，资源可以正常释放。
6. 集群或网络暂时不可用时，HTML 控制台和 MCP 能显示明确的不可用状态。
